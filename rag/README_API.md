# RAG Intervention Recommendation Workflow

## Overview

The RAG (Retrieval-Augmented Generation) workflow generates member-specific intervention recommendations using existing prediction and SHAP data from the backend database.

The workflow combines:

* Existing member information
* Risk prediction results
* SHAP risk drivers
* Intervention-specific mappings
* FAISS-based evidence retrieval
* Gemini-based recommendation generation
* Recommendation validation
* Database persistence

The RAG layer does **not** run the prediction pipeline or calculate SHAP values. It consumes the prediction and SHAP information that has already been generated by the backend.

---


## Recommendation Generation

The recommendation generator follows these stages:

### 1. Load Existing Database Context

The RAG workflow loads:

* Member
* Latest `RiskPrediction`
* Latest `ShapExplanation`

The workflow does not create a new prediction.

A prediction must already exist for the member before recommendations can be generated.

---

### 2. Build RAG Context

The member's existing database information is converted into an intervention-oriented RAG context.

The context includes:

* Member information
* Risk score
* Risk category
* SHAP drivers
* Intervention drivers
* Feature values
* Intervention concepts
* Intervention domains

---

### 3. Intervention-Specific Retrieval

The RAG workflow maps relevant SHAP intervention drivers to intervention concepts and performs evidence retrieval.

FAISS is used to retrieve evidence relevant to each intervention.

Retrieved evidence contains metadata such as:

```text
source
domain
topic
document
chunk_id
score
```

Only evidence returned by the RAG retrieval layer is allowed to support a recommendation.

---

## Gemini Recommendation Generation

Gemini receives the member-specific RAG context and retrieved evidence.

The model is instructed to:

* Use only supplied member information.
* Use only supplied intervention features.
* Respect the actual member feature values.
* Ground recommendations in retrieved evidence.
* Use exact evidence `chunk_id` values.
* Preserve the supplied SHAP impact.
* Avoid inventing diagnoses or clinical information.
* Avoid prescribing medication or medication dosage.
* Recommend care-team review when information is insufficient.

The generated response is expected to be valid JSON.

---

## Recommendation Validation

Gemini output is validated before it is returned or stored.

Validation ensures that:

1. The recommendation feature exists in the RAG intervention context.
2. The SHAP impact comes from the actual intervention data.
3. Evidence belongs to the corresponding intervention.
4. Evidence `chunk_id` exists in the actual RAG retrieval results.
5. Evidence metadata comes from the RAG pipeline rather than being trusted from Gemini.
6. Recommendations contain real retrieved evidence.
7. Risk score and risk category come from the actual prediction/RAG context.
8. Recommendations are limited to the configured maximum.

If Gemini omits valid evidence metadata, the validator can use the actual retrieved RAG evidence rather than fabricating evidence.

---

## Database Persistence

Generated recommendations are persisted in the `interventions` table.

The relevant fields are:

```text
member_id
prediction_id
intervention_priority
recommendations
source
status
created_at
```

Example:

```text
member_id = M00001
prediction_id = 148
source = RAG
status = PENDING
intervention_priority = HIGH
```

The complete validated recommendation list is stored in the `recommendations` JSON column.

---

## Recommendation Reuse

The recommendation API does not regenerate recommendations every time it is called.

For:

```text
GET /recommendations/{member_id}
```

the service first checks whether an RAG intervention already exists for the member's latest prediction.

The lookup is based on:

```text
member_id
prediction_id
source = RAG
```

If an intervention already exists:

```text
Database
   |
   v
Existing Intervention
   |
   v
Return stored recommendations
```

Gemini and FAISS are not called again.

If an intervention does not exist:

```text
Database
   |
   v
No Intervention
   |
   v
Run RAG
   |
   v
Generate + validate recommendation
   |
   v
Save Intervention
   |
   v
Return recommendation
```

This prevents unnecessary repeated LLM calls and keeps recommendations associated with the prediction that produced them.

---

## Prediction Versioning

An intervention is associated with a `prediction_id`.

Therefore:

```text
Member M00001
    |
    +-- Prediction 148
    |      |
    |      +-- Intervention
    |
    +-- Prediction 149
           |
           +-- New Intervention
```

If the member receives a new prediction, the new `prediction_id` allows the system to generate and persist a new recommendation set.

Existing recommendations for the previous prediction remain associated with that previous prediction.

---

## SHAP Relationship

`ShapExplanation` does not need to be duplicated inside the `Intervention` table.

The relationship is:

```text
RiskPrediction
      |
      +---- ShapExplanation
      |
      +---- Intervention
```

The intervention stores the validated recommendation snapshot, including the relevant `shap_impact`.

The original SHAP explanation remains available through the corresponding prediction.

## API

### Get Member Recommendations

```http
GET /recommendations/{member_id}
```

Example:

```http
GET /recommendations/M00001
```

The endpoint:

1. Validates the member ID.
2. Finds the member.
3. Finds the latest prediction.
4. Checks for an existing RAG intervention.
5. Returns the stored recommendation if available.
6. Otherwise runs the RAG pipeline.
7. Persists the generated intervention.
8. Returns the validated recommendation.

## Important Grounding Rules

The RAG workflow must not:

* Invent diagnoses.
* Invent medications.
* Invent medication dosage.
* Invent laboratory values.
* Invent member history.
* Invent smoking status.
* Invent evidence.
* Invent evidence sources.
* Invent evidence chunk IDs.
* Create unsupported intervention features.
* Treat FAISS similarity alone as proof of clinical appropriateness.

The retrieved evidence supports the recommendation but does not replace clinical judgment.

## Components

The main components of the workflow are:

```text
rag/
├── intervention/
│   ├── recommendation_generator.py
│   ├── context_builder.py
│   ├── intervention_retriever.py
│   └── outputs/
│
backend/
└── app/
    ├── api/
    │   └── prediction.py
    ├── services/
    │   ├── rag_service.py
    │   └── intervention_service.py
    └── database/
        └── models.py
```

### `context_builder.py`

Builds the member-specific RAG context from existing database prediction and SHAP information.

### `intervention_retriever.py`

Maps intervention drivers to retrieval queries and retrieves supporting evidence using FAISS.

### `recommendation_generator.py`

Coordinates:

```text
Database
→ RAG context
→ FAISS retrieval
→ Gemini
→ JSON parsing
→ Validation
```

### `intervention_service.py`

Handles recommendation persistence and reuse.

It prevents unnecessary RAG/Gemini execution when an intervention already exists for the latest prediction.

### Recommendation API

Exposes:

```http
GET /recommendations/{member_id}
```

## Testing the Workflow

### First request

Run:

```text
GET /recommendations/M00001
```

If no intervention exists for the latest prediction:

```text
RAG retrieval
    ↓
Gemini generation
    ↓
Validation
    ↓
Intervention INSERT
```

### Second request

Run the same request again:

```text
GET /recommendations/M00001
```

The existing intervention should be returned directly:

```text
Intervention SELECT
    ↓
Return stored recommendations
```

FAISS and Gemini should not be executed again.

### New prediction

After a new prediction is created:

```text
POST /predict
```

the new prediction receives a new `prediction_id`.

The next recommendation request can then generate a new intervention associated with that prediction.
